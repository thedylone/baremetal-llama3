Bare-Metal Llama 3

An inference engine for Llama-3-8B-Instruct written from scratch in C++17 and CUDA for Harvard CS 265. It uses no PyTorch or cuBLAS at runtime: every operator in the forward pass, from the embedding lookup to the final logits, is a hand-written kernel.

01 — Overview

What it is

The project rebuilds the Llama-3-8B-Instruct forward pass at the level of raw device pointers. A Python dumper converts the HuggingFace safetensors checkpoint into a simple per-tensor binary format. The C++ side memory-maps those files, converts BF16 to FP32, uploads to the GPU and runs the model through its own CUDA kernels.

A byte-level BPE tokenizer, also in C++, handles encoding and decoding. A greedy decoding loop generates tokens one at a time by taking the argmax over the 128,256-entry logits.

Correctness is checked operator by operator. Reference fixtures are generated from PyTorch implementations (reference.py, tools/generate_*_reference.py). An 18-case test suite compares the CUDA path against them, covering tokenization, embeddings, matmul, RMSNorm, RoPE, GQA, residual add, SiLU gating, the SwiGLU FFN, a full decoder block, a single forward step and multi-token generation.

The work was profiled with Nsight Systems and Nsight Compute; the reports' findings are below.

02 — Architecture

From checkpoint to next token

The pipeline has four stages: getting the weights onto the GPU, then the decoding loop, which runs the 32-layer stack once per generated token.

01

Dump

tools/dumper.py writes each safetensors tensor to its own .bin file (magic number, name, shape, dtype and raw BF16 bytes) plus a metadata.json index.

02

Mmap

An RAII MappedFile class mmaps each tensor read-only and unmaps it when it goes out of scope. A 16-bit shift on the CPU turns BF16 values into FP32.

03

Upload

Projection matrices are transposed on the CPU to [in, out] and copied to device memory. The embedding table, final norm and LM head are uploaded once, at load time.

04

Decode

Each new token runs the forward pass over the whole sequence, takes the argmax of the last position's logits and appends it. RoPE tables are precomputed on the GPU for up to 1,000 positions.

After the 32 layers come a final rms_norm and a single-row sgemm against the LM head ([1, 4096] × [4096, 128256]), for the last position only. The four attention kernels run once per query head, and each KV head is shared by four query heads.

Lazy layer loading

Per-layer weights are not kept on the GPU. forward() loads a batch of layers (LAZY_LOAD_BATCH_SIZE, default 1), runs them, synchronises and frees them unless LAZY_LOAD_KEEP_LAYERS is set. The full FP32 model, about 32 GB, never has to be resident at once. The cost is re-reading weights on every step.

No KV cache, by design

Each step recomputes K and V for the entire prefix. Scratch buffers are allocated once for the maximum sequence length and reused across steps. The report works out the consequence: generating T tokens costs O(T²) total work without caching, against O(T) with it.

03 — Kernels

How the kernels work

Every kernel is FP32 and hand-written. The main techniques are shared-memory tiling, tree reductions in shared memory, register blocking, and keeping each warp's global loads contiguous.

SGEMM

src/gemm.cu · three variants

All seven projections per layer, and the LM head, go through one sgemm(A, B, C, M, N, K, α, β) entry point. It currently dispatches to the fastest of three implementations, and each one is checked against a CPU reference in benchmarks/benchmark_gemm.cu.

Naive
  • One thread per output element, in 32×32 blocks.
  • Every operand comes straight from global memory.
Shared-memory tiled
  • 32×32 output tile per block; K is walked in 32-wide tiles.
  • Adjacent threads load adjacent columns, so tile loads are coalesced.
Register-tiled · in use
  • 64×64 block tile, BK = 32, 64 threads.
  • Each thread keeps an 8×8 accumulator in registers and does an outer product per k-step.
// inner loop of sgemm_register_tiled_kernel (BM=BN=64, BK=32, TM=TN=8)
for (int k = 0; k < BK; ++k) {
  for (int i = 0; i < TM; ++i) rA[i] = sA[ty * TM + i][k];
  for (int j = 0; j < TN; ++j) rB[j] = sB[k][tx * TN + j];
  for (int i = 0; i < TM; ++i)
    for (int j = 0; j < TN; ++j) acc[i][j] += rA[i] * rB[j];
}

RMSNorm

src/rms_norm.cu
  • One 256-thread block per row; threads stride across d = 4096.
  • Per-thread partial sums of x² are combined with a shared-memory tree reduction.
  • Thread 0 computes rsqrtf(mean + ε) and broadcasts it through shared memory. A second pass applies x · inv_rms · γ.
  • Reading the row twice costs 16d bytes of HBM traffic per row. The report estimates that keeping the row in shared memory would cut that by 25%.

Grouped-query attention

src/attention.cu
  • 32 query heads map onto 8 KV heads (g = i / 4), so no K/V data is duplicated.
  • score: a 16×16 thread grid with one dot product of length 128 per (query, key), scaled by 1/√128.
  • causal_mask: sets entries above the diagonal to a large negative value.
  • softmax: one block per row. A shared-memory max reduction, then exp and a sum reduction, keep it numerically stable.
  • output: aiV, written straight into the concatenated head layout.

SwiGLU FFN

src/silu.cu + sgemm
  • The gate and up projections (4096 → 14,336) are two SGEMMs.
  • A fused element-wise kernel computes silu(gate) * up in place, which saves a separate multiply pass.
  • The down projection (14,336 → 4096) is the third SGEMM.

RoPE, embedding and residual

src/rope.cu · model.cu
  • Cos/sin tables for θ base 500,000 are precomputed on the GPU at load time.
  • rope_apply uses one block per (head, position) and one thread per rotation pair (i, i + 64), applied in place to Q and K.
  • Embedding lookup uses one block per token with a strided, coalesced row copy. Residual add is a single element-wise kernel.

      05 — Analysis

      Back-of-envelope numbers

      Score matrices

      All 32 attention score matrices at s = 512 in FP32 take 32 MB. They grow as 128s² bytes and would outweigh the whole model's weights beyond s ≈ 15,841.

      QKV and L2

      Q, K and V are three launches over the same Xnorm. On a 48 MB L2 (the course cluster's L4), Xnorm fits for s ≤ ~2,930, which would save 66.7% of that read traffic. A 3 MB laptop L2 fits only ~183 tokens.

      Without a KV cache

      Generating T tokens from a prompt of length s0 costs Σ F(s0 + t), which is O(T²). Caching K and V makes each step's work constant, so the total is O(T).
