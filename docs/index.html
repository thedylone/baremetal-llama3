01 · Overview

What it is

The project rebuilds the Llama-3-8B-Instruct forward pass at the level of raw device pointers. A Python dumper converts the HuggingFace safetensors checkpoint into a simple per-tensor binary format; the C++ side memory-maps those files, converts BF16 to FP32, uploads to the GPU and runs the model through its own CUDA kernels.

A byte-level BPE tokenizer (also C++) handles encoding and decoding, and a greedy decoding loop generates tokens one at a time by taking the argmax over the 128,256-entry logits.

Correctness is checked operator by operator. Reference fixtures are generated from PyTorch implementations (reference.py, tools/generate_*_reference.py), and an 18-case test suite compares the CUDA path against them: tokenization, embeddings, matmul, RMSNorm, RoPE, GQA, residual add, SiLU gating, the SwiGLU FFN, a full decoder block, a single forward step and multi-token generation.

The work was profiled with Nsight Systems and Nsight Compute, and the reports' findings are on this page.

02 · Architecture

From checkpoint to next token

The pipeline has four stages: getting weights onto the GPU, then the decoding loop that runs the 32-layer stack once per generated token.

  1. Dump

    tools/dumper.py writes each safetensors tensor to its own .bin file (magic number, name, shape, dtype, raw BF16 bytes) plus a metadata.json index.

  2. mmap

    An RAII MappedFile class mmaps each tensor read-only and unmaps it when it goes out of scope. BF16 values become FP32 with a 16-bit shift on the CPU.

  3. Upload

    Projection matrices are transposed on the CPU to [in, out] layout and copied to device memory. The embedding table, final norm and LM head are uploaded once at load time.

  4. Decode

    For each new token, run the forward pass over the whole sequence, take the argmax of the last position's logits, append it and repeat. RoPE cos/sin tables are precomputed on the GPU for up to 1,000 positions.

After the 32 layers come a final rms_norm and a single-row sgemm against the LM head ([1, 4096] × [4096, 128256]) for the last position only. The four attention kernels run once per query head, and each KV head is shared by four query heads.

Lazy layer loading

Per-layer weights are not held on the GPU permanently. forward() loads a batch of layers (LAZY_LOAD_BATCH_SIZE, default 1), runs them, synchronises and frees them unless LAZY_LOAD_KEEP_LAYERS is set. The full FP32 model, about 32 GB, never has to be resident at once. The cost is re-reading weights on every step.

No KV cache, by design

Each step recomputes K and V for the entire prefix. Scratch buffers are preallocated once for the maximum sequence length and reused across steps. The report works out the consequence: generating T tokens costs O(T²) total work without caching, against O(T) with it.

03 · CUDA kernels

The kernels

Every kernel is FP32 and written by hand. The main techniques are shared-memory tiling, tree reductions in shared memory, register blocking, and keeping each warp's global loads contiguous.

SGEMM src/gemm.cu · three variants

All seven projections per layer, and the LM head, go through one sgemm(A, B, C, M, N, K, α, β) entry point. It currently dispatches to the fastest of three implementations, each checked against a CPU reference in benchmarks/benchmark_gemm.cu.

Naive
  • One thread per output element, 32×32 blocks.
  • Every operand comes straight from global memory.
Shared-memory tiled
  • 32×32 output tile per block, K walked in 32-wide tiles.
  • Adjacent threads load adjacent columns, so tile loads are coalesced.
Register-tiled · in use
  • 64×64 block tile, BK = 32, 64 threads.
  • Each thread keeps an 8×8 accumulator in registers and does an outer product per k-step.
// inner loop of sgemm_register_tiled_kernel (BM=BN=64, BK=32, TM=TN=8)
for (int k = 0; k < BK; ++k) {
  for (int i = 0; i < TM; ++i) rA[i] = sA[ty * TM + i][k];
  for (int j = 0; j < TN; ++j) rB[j] = sB[k][tx * TN + j];
  for (int i = 0; i < TM; ++i)
    for (int j = 0; j < TN; ++j) acc[i][j] += rA[i] * rB[j];
}

RMSNorm src/rms_norm.cu

  • One 256-thread block per row; threads stride across d = 4096.
  • Per-thread partial sums of x² are combined with a shared-memory tree reduction.
  • Thread 0 computes rsqrtf(mean + ε) and broadcasts it through shared memory. A second pass applies x · inv_rms · γ.
  • Reading the row twice costs 16d bytes of HBM traffic per row. The report estimates that keeping the row in shared memory would cut 25% of that.

Grouped-query attention src/attention.cu

  • 32 query heads map onto 8 KV heads (g = i / 4), so no K/V data is duplicated.
  • score: a 16×16 thread grid, one dot product of length 128 per (query, key), scaled by 1/√128.
  • causal_mask: sets entries above the diagonal to a large negative value.
  • softmax: one block per row. A shared-memory max reduction, then exp and a sum reduction, give a numerically stable result.
  • output: aiV written directly into the concatenated head layout.

SwiGLU FFN src/silu.cu + sgemm

  • Gate and up projections (4096 → 14,336) are two SGEMMs.
  • A fused element-wise kernel computes silu(gate) * up in place, which saves a separate multiply pass.
  • The down projection (14,336 → 4096) is the third SGEMM.

RoPE, embedding, residual src/rope.cu · model.cu

  • cos/sin tables for θ base 500,000 are precomputed on the GPU at load.
  • rope_apply uses one block per (head, position) and one thread per rotation pair (i, i + 64), applied in place to Q and K.
  • Embedding lookup uses one block per token, with a strided, coalesced row copy. Residual add is a single element-wise kernel.

      05 · From the reports

      Back-of-envelope numbers

      Score matrices

      All 32 attention score matrices at s = 512 in FP32 take 32 MB. They grow as 128s² bytes and would exceed the entire model's weights beyond s ≈ 15,841.

      QKV and L2

      Q, K and V are three launches that read the same Xnorm. On a 48 MB L2 (the course cluster's L4), Xnorm fits for s ≤ ~2,930, which would save 66.7% of that read traffic. A 3 MB laptop L2 fits only ~183 tokens.

      Without a KV cache

      Generating T tokens from a prompt of length s0 costs Σ F(s0 + t), which is O(T²). Caching K and V makes each step's work constant, so the total is O(T).
